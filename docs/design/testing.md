# 网球总监 · 测试文档 v0.2

Oct 29, 2026 · @Enting · 2026-11-01 按 Indian Wells 版本和现有测试重写（v0.2）

## 测试目标与范围

测试要回答三个问题：模拟算得对不对，内容写得对不对，玩起来是不是设计文档想要的感受。前两个靠自动化，第三个靠评审代理和真人试玩。

玩法以 [玩法设计文档 v0.3](game-design.md) 为准，实现以 [技术架构文档](architecture.md) 和 `docs/adr/` 为准。本文写的是**现在有什么、怎么跑、什么算过**；还没有的写在"待补的测试"和"待定事项"里。

| 测试对象 | 主要手段 | 现状 |
| --- | --- | --- |
| 模拟核心：时钟、命令、岗位和工单、习惯、衰减、事件引擎、导演、存档 | 单元测试、确定性测试 | 有，`packages/sim/src/sim.test.ts` |
| 内容数据：地图、设施、岗位、工单、事件卡、人物、文案 | 构建时校验、编译器测试、机器人跑局 | 有 |
| 画面和模拟对得上：锚点、步道、球场、演出 | 组装测试 | 有，`apps/game` |
| 玩法体验：复原的感受、有趣的选择、节奏 | 评审代理（试玩桥）、真人试玩 | 评审代理有；真人试玩还没开始 |
| 画面回归 | 截图对比 | 2026-11-01 随 Hollow Creek 一起删掉了，等精细场景（P3）再按 Indian Wells 重建 |

不覆盖：联网和云存档（纯前端）、音频。

## 测试分层

越靠上越快、越多、越自动；越靠下越慢、越贵、越依赖人。经营游戏的组合没人能全部手测，所以重心放在模拟和内容上，用机器人跑局兜底。

| 层 | 回答的问题 | 工具 | 何时跑 |
| --- | --- | --- | --- |
| 1 内容校验 | 数据写得合法吗，引用都存在吗 | `pnpm content`（Zod + 编译器），开发时热重载 | 每次保存、CI |
| 2 单元测试 | 每个系统、条件、效果算得对吗 | Vitest，`pnpm test` | 每次提交、CI |
| 3 确定性 | 同样的输入是否永远得到同样的结果 | `sim.test.ts`、`pnpm sim determinism` | CI；改模拟后跑 1000 局 |
| 4 机器人跑局 | 能通关吗，有没有卡死、永不出现的卡、太难太易 | `balance.test.ts`、`pnpm sim bots`、`pnpm sim playability` | CI 跑区间；改数值后重出报告 |
| 5 组装和画面 | 模拟、画面、界面对得上吗，核心流程走得通吗 | `apps/game` 的测试；手动截图 | CI；改画面时手动 |
| 6 玩法评审 | 好玩吗，守住玩法准则了吗 | 试玩桥 + 评审代理；真人 | 每个大改动后一轮 |

分工原则：能在第 1 层发现的错误，不要等到第 4 层；能在第 4 层发现的错误，不要等到人去玩。

## CI

`.github/workflows/ci.yml`，每次推到 main 和每个 PR 都跑，任何一步失败就红：

1. `pnpm typecheck`：所有工作区的类型检查（TypeScript 7）。
2. `pnpm lint`：Biome 格式和规范（行宽 120、单引号、尾逗号、import 排序）。
3. `pnpm check:deps`：分层规则（dependency-cruiser）。sim 不能依赖 iso、ui、three.js、Preact；shared 是最底层；iso 和 ui 互不引用，iso 不依赖 three 和 Preact。
4. `pnpm test`：全部 Vitest 测试，包括平衡区间。
5. `pnpm build`：游戏和 sandbox 都能构建。

内容 JSON 和 YAML 不一致（改了 YAML 忘了 `pnpm content`）时，编译器测试会失败。

## 单元测试和内容校验

### 模拟核心（`packages/sim/src/sim.test.ts`）

模拟是纯函数：输入状态和命令，输出新状态和领域事件。每条测试都是"给定状态 → 执行 → 断言状态"，不需要浏览器。现在的覆盖：

| 模块 | 测什么 |
| --- | --- |
| 开局 | 按地图配置建好状态（第 1 天 8:00、秋天、总监在大门、Dale 在会所、全部废弃）；开局的卡打开并请求暂停；第一天能做的只有扫外场 1 和发传单 |
| 走路和指派 | 导航图最短路和分钟数；到了才开始干；不能指派的情况（没招的人、还没开出来的岗位、钱不够的工单） |
| 修复就是解锁 | 扫沙 → 换网 → 外场 1 能打，开出三个岗位、冒出下一批修复；修复的前提链；表演赛通关 |
| 岗位 | 时段里有人才转圈、每圈结算、收盘合成一条因果日志；中途拉走丢一圈、退回服务分钟；顶替；没人服务计入服务率分母、周日结算后清零 |
| 工单 | 第一个人到场扣材料费；拉走进度保留；做完设施换状态、状况加上去；多人更快、人数上限 |
| 习惯 | 记住派过的班、自己去上下一个班；工单不进习惯；做工单的人班一开始去上班、下班回来接着做；按习惯换班不算"白干了" |
| 总监成长 | 干一圈涨 0.3、员工不涨；跨过整十发事件 |
| 衰减 | 放一天几乎不动、一天掉 decay_day；状况低于 30 质量贡献减半；低于 40 冒出清理工单；维护岗位按能力修复 |
| 事件卡 | 要总监亲自去办的选项；钱不够不能选；倒计时到了执行默认；大风扬沙改状况；后续卡带原因链；只出现一次；招聘日（从大门进来、工资、主教练交接）；辞掉主教练后 Dale 接回 |
| 时间 | 收盘结算、夜里跳过；换季和天气；不操作时会员只在周日变；第 112 天期限 |
| 条件 | all / any / not、状态量、标记、设施、主教练、修好了几处 |
| 确定性 | `step` 不改输入；同种子同命令日志重放哈希一致；同种子两次一样、换种子不一样；状态能 JSON 往返 |
| 存档 | 往返后接着跑结果一样；v0 → v5 逐级迁移；坏档和更新版本报错、内容版本不一致只警告 |
| 整局 | 贪心机器人打得完、日志有原因；放置不管的对照局期限到了、什么都没修好 |

### 内容校验（`packages/content/src/compile.ts` 和 `compile.test.ts`）

构建时、热重载时都跑，错误阻止构建，警告打在终端和调试面板里：

- **错误：**schema 不合法；引用了不存在的卡、活动、地点、状态量、设施或设施状态、人物；表达式语法错或用了未知变量；倒计时卡没有默认后果；文案缺键（两种语言都要有）；文件名和 id 不一致。
- **警告：**只被读、从没被写的标记；两个选项效果完全相同；选项只改了暗处的标记（准则 2）；永远不会被安排的卡；岗位没有效果也不修复；工单没有效果。
- **编译器测试**故意把仓库里的真实内容改坏（错的地点、拼错的状态量和变量、删掉默认后果和文案、改错文件名），确认每种错误都能报出来；还检查 Indian Wells 有开局、招聘日、期限这几张必须的卡，每个设施都有修复工单。

## 确定性

设计上，种子加命令日志就是一局的全部。所以 bug 复现几乎没有成本。

| 检查 | 做法 | 通过标准 | 现状 |
| --- | --- | --- | --- |
| 重放一致 | 同一种子 + 同一命令日志跑两遍 | 状态哈希相同 | 有（单元测试 + `pnpm sim determinism --games 1000`） |
| 存读档一致 | 中途存档、读档再继续，对比一口气跑完 | 状态哈希相同 | 有 |
| 有无画面一致 | 浏览器里带渲染跑，和命令行无头跑 | 状态哈希相同；不同说明画面层偷偷改了状态 | 待补 |
| 变速一致 | 1×、2×、中途暂停跑同一局 | 状态哈希相同 | 待补（模拟按分钟推进，理论上成立） |

模拟里不用 `Math.random`，只用状态里的种子随机数（CLAUDE.md）。

## 机器人跑局和平衡

模拟不依赖画面，所以可以在命令行里让不同打法的机器人各跑几百局，用统计结果发现单元测试发现不了的问题。

### 机器人（`packages/sim/src/bots.ts`）

| 机器人 | 打法 | 用来发现 |
| --- | --- | --- |
| 贪心型 greedy | 每 15 分钟给每个人挑最值得去的地方（有客人的岗位、划算的工单、状况掉下来的维护），什么人都招，钱留得少 | 会玩的上限：能不能在期限内通关、多早通关 |
| 谨慎型 cautious | 卡选最坏情况最不坏的，不赌判定，钱留得多，**从不招人** | 不招人能不能通关（不应该：招人是核心玩法） |
| 随机型 random | 卡随机选、有时放着过期；偶尔随手把一个人拖到随便一个岗位或工单上 | 乱玩也能通关说明太简单 |
| 放置型 idle | 什么都不做，卡全部走默认 | 准则 6：放着不管会慢慢变差，但不会一下崩掉；不应该赢 |

### 平衡区间（`apps/sim-cli/src/balance.test.ts`，CI 每次跑，每种 30 局）

| 指标 | 区间 | 现在（200 局，`docs/balance/indian-wells.md`） |
| --- | --- | --- |
| 贪心型通关率 | ≥ 60% | 99% |
| 谨慎型（不招人）通关率 | ≤ 20% | 0% |
| 随机型通关率 | ≤ 20% | 0% |
| 放置型通关率 | = 0% | 0% |
| 卡死的局 | 0 | 0 |
| 从未出现的卡 | 无 | 无 |
| 贪心型平均通关天数 | > 70 天（表演赛是结尾，不是第 6 周） | 100 天 |

贪心型接近一个完美的排班员，所以它的通关率不能代表真人。真人的区间等第一轮真人试玩后再定（见"待定事项"）。

### 报告

```bash
pnpm sim bots --games 200 > docs/balance/indian-wells.md     # 通关率、结局分布、平均状态、每张卡出现的比例
pnpm sim playability --games 60 --out docs/balance/playability.md   # 节奏、取舍、后果分叉
pnpm sim determinism --games 1000                            # 确定性闸口
```

改了平衡相关的数值，重跑前两份报告一起提交（CLAUDE.md）。可玩性报告看三件事：

- **节奏：**1× 下每隔多少秒真实时间有一个决定、营业时间里最长的无卡空档。注意它只数卡，不数拖人，所以"空档"偏长是正常的。
- **取舍：**每张卡各选项被选的比例，加上静态分析出的被压制选项（应该是 0）。
- **后果分叉：**同一种子、不同打法见过的卡有多不同（Jaccard 距离）。

## 玩法评审

机器人能告诉你能不能通关，不能告诉你好不好玩。

### 评审代理（试玩桥）

`tools/playtest/server.mjs` 在无头 Chromium 里打开构建好的游戏（默认手机竖屏），用 HTTP 一步一步地玩：`/state` 看玩家眼前的一切，`/pick`、`/tap`、`/assign` 拖人，`/answer` 选卡，`/wait` 让时间走，`/shot` 截图。评审说明在 `tools/playtest/brief.md`。

- 每轮至少两个评审代理：一个新手、一个老手，各用不同的种子玩完一局，另跑一局放置不管的对照。
- 评审代理只能通过试玩桥玩，不读代码和内容。
- 按九项打分（有意义的选择、看得懂的后果、节奏、主动性、放置时世界照常运转、张力曲线、重玩价值、上手、手机体验），逐条对照准则 1–6，给出最伤体验的五个问题和改法。
- 结果记在 `docs/design/backlog.md`。第一、二轮（Hollow Creek）的分数和结论留在那里作参考；Indian Wells 的第一轮还没做（backlog GM-1）。

### 真人试玩

还没开始。计划：

- **人数和人选：**每轮 5 名没玩过的新玩家，一半玩过经营游戏（Kairosoft、Two Point 类），一半没玩过；至少 1 名网球爱好者。
- **过程：**只给一句开场："你是这座废弃网球园区的新总监。"在手机上玩，边玩边说出想法；卡住超过 2 分钟才介入并记录。录屏，结束后用调试面板导出存档和命令日志。
- **问卷：**用一句话说说你在做什么；哪个决定最难；有没有"莫名其妙就发生了"的事；想不想再玩；节奏和难度各 1–5 分。

### 要验证的设计假设

| 假设 | 观察什么 | 通过标准（建议） |
| --- | --- | --- |
| 玩家感到"复原" | 结束时问"园区比开始时活过来了吗"；情绪的高点在哪 | 多数人能说出一个"修好了"的时刻 |
| 拖人是核心，不是等卡 | 主动派人次数和回应卡片次数之比 | 主动派人远多于回应卡片 |
| 人手稀缺带来取舍 | 有没有为了修东西放下赚钱的岗位、或者反过来 | 多数人至少一次说出"人不够" |
| 开局看得懂 | 第一次把人拖到扫沙上用了多久、求助次数 | 2 分钟内无提示完成 |
| 招人有取舍 | 不同玩家在同一个招聘日选了谁；访谈"你犹豫过吗" | 每个招聘日两个候选人都有人选 |
| 16 周期限的压力合适 | 通关天数、最后几周的感受 | 多数人在最后两周内办成或差一点，不觉得不公平 |
| 因果日志读得懂 | 事后挑一个延迟后果，让玩家解释原因 | 5 人中至少 3 人能说对 |
| 放着不管世界照常运转 | 放一会儿再回来，看画面和数字 | 玩家能指出没人管的地方变差了 |

不成立的假设要么改设计，要么改假设本身，并同步回设计文档。

## 缺陷管理

每个 bug 都必须能一键复现：调试面板（\` 键，正式版里没有）导出"存档 + 命令日志 + 种子 + 内容版本"。没有这个附件的报告，先补附件再处理。修复流程：用附件重放复现 → 修复 → 把这份命令日志加进测试 → 合并。

| 级别 | 定义 | 例子 | 处理 |
| --- | --- | --- | --- |
| S1 | 崩溃、存档损坏、卡死 | 读档后白屏；修复链断了，什么都开不出来 | 立即修，阻塞合并 |
| S2 | 规则或数值错误，卡永不触发，画面和结果不一致 | 倒计时到期没执行默认；修好了画面没变 | 当前迭代内修 |
| S3 | 画面错误 | 地点牌叠在一起；人走到场地里面 | 排期修 |
| S4 | 文案和小瑕疵 | 英文溢出事件卡 | 排期修 |

手测某张卡不用从头玩：用调试面板强制打开这张卡、改好需要的状态量和标记、跳过时间。查"这张卡为什么没出来"时，看面板里此刻满足条件的卡和它们的权重。
