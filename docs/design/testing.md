# 网球总监 · 测试文档 v0.1

Oct 29, 2026 · @Enting

## 测试目标与范围

测试要回答三个问题：模拟算得对不对，内容写得对不对，玩起来是不是设计文档想要的感受。前两个靠自动化，第三个只能靠人玩。

玩法以 [玩法设计文档 v0.1](https://claude.ai/artifact/L928nnUJivRPVhUzZXnrBi) 为准，实现以 [技术架构文档 v0.1](https://claude.ai/artifact/Cy2ae8npLfYgtEwufEtr7s) 为准。本文把技术文档"工程实践"里的四层测试展开成可执行的方案。第一个要通过的测试闸口是 M2：Hollow Creek 前 15 分钟的垂直切片。

| 测试对象 | 依据 | 主要手段 |
| --- | --- | --- |
| 模拟核心：时钟、命令、7 个系统、事件引擎、导演 | 技术文档"模拟核心" | 单元测试、确定性测试 |
| 内容数据：事件卡、活动、状态量、导演配置、文案 | 技术文档"内容管线"、设计文档"事件卡规格" | 构建时校验、事件卡用例、机器人跑局 |
| 存档、迁移、跨幕继承 | 技术文档"存档与版本迁移" | 回放测试、旧存档样本 |
| 表现层：场景、活动演出、HUD | 技术文档"表现层" | 画面回归、端到端冒烟 |
| 玩法体验：三幕的美感目标、有趣的选择 | 设计文档"概述""设计检查清单" | 玩法测试（Playtest） |

不覆盖：联网和云存档（目前是纯前端）、音频。具体数值还没定，本文只定测量方法和阈值框架，阈值初值都标为"建议"，跑出第一批数据后校准。

## 测试策略总览

测试分六层，越靠上越快、越多、越自动；越靠下越慢、越贵、越依赖人。事件驱动的经营游戏，卡与卡的组合没人能全部手测，所以重心放在模拟和内容上，用机器人跑局兜底。

| 层 | 回答的问题 | 工具 | 何时跑 | 量级 |
| --- | --- | --- | --- | --- |
| 1 内容校验 | 数据写得合法吗，引用都存在吗 | Vite 插件 + Zod | 每次保存、每次构建 | 全部内容 |
| 2 单元测试 | 每个系统、条件、效果算得对吗 | Vitest | 每次提交 | 数百条，1 分钟内跑完 |
| 3 确定性与回放 | 同样的输入是否永远得到同样的结果 | Vitest + 回放集 | 每次提交 | 每个已修 bug 一条回放 |
| 4 机器人跑局 | 能通关吗，有没有卡死、永不出现的卡、绝对正确的选项 | `apps/sim-cli` | 每晚，内容改动后 | 每种机器人每幕 1000 局 |
| 5 画面回归与端到端 | 画面变了吗，核心流程能走通吗 | Playwright | 每个 PR | 每场景 4 角度 + 冒烟流程 |
| 6 玩法测试 | 好玩吗，玩家感受到设计目标了吗 | 真人 + 问卷 + 录屏 | 每两周一轮，从 M2 起 | 每轮 5 名新玩家 |

分工原则：能在第 1 层发现的错误，不要等到第 4 层；能在第 4 层发现的错误，不要等到人去玩。

## 单元测试与内容校验

模拟核心是纯函数，输入状态和命令，输出新状态和领域事件，所以每条测试都是"给定状态 → 执行 → 断言状态"，不需要浏览器。

### 模拟核心必测点

| 模块 | 必测点 | 例子 |
| --- | --- | --- |
| 条件语言 | all / any / not 组合；比较的边界；引用不存在的状态量要报错，不能静默当成 false | 现金正好 500 时 `{stat: cash, lt: 500}` 为假 |
| 效果执行 | 只能执行白名单效果；状态量按注册范围截断；每个效果都写入因果日志并带原因 | 声望不会低于 0；日志条目带 `card` 和 `option` |
| 倒计时 | 到期执行默认后果和 `extra`；暂停时不减少；正好在 tick 边界到期只结算一次 | 匹克球卡 2 天后默认执行 A，声望 −5 |
| 抽卡、权重、冷却 | 冷却中的卡不进候选；固定种子下抽卡结果固定；1 万次抽取的分布符合权重 | 权重 3 和 1 的两张卡，抽中比例约 3:1 |
| 总监系统 | 需要亲临的选项在到达前不可选；路径时长按导航图算；在场修正只作用于附近的人 | 总监不在 2 号场时，匹克球卡只能选 A、B |
| 活动结算 | 同输入同种子同结果；结果里带演出需要的关键时刻 | 训练输出"体力 −12、技术 +3、摔倒 1 次" |
| 人员系统 | 疲劳恢复、士气漂移、受伤判定 | 疲劳超过阈值后受伤概率上升 |
| 日历与经济 | 日历事件按日期触发；收支按周结算一次 | 第 7 天结束时只结算一次周收入 |
| 导演 | 压力高时危机卡权重下降、压力低时上升；三份导演配置各自生效 | 未处理卡数 ≥ 3 时不再发危机卡（阈值待定） |
| 存档迁移 | 每个迁移函数用对应的旧版本存档样本测试，升级后通过当前 schema | `0004_add_stakeholders` 后存在五条利益方满意度 |
| 跨幕继承 | `carryOver` 只输出允许继承的字段；现金和设施不继承；未选中的人不出现 | Hollow Creek 的现金不会带进枫岭 |

### 事件卡用例

每张事件卡至少配一组用例，和卡的 YAML 放在一起。用例只描述"从什么状态出发、做什么、应该变成什么"，策划也能写。下面是匹克球租场卡的示意写法（函数名待实现时确定）：

```ts
test('总监不在 2 号场时，选项 C 不可选', () => {
  const s = openCard(fixture('hc_start', { cash: 400, reputation: 50 }), 'hc_pickleball_court2');
  expect(availableOptions(s, 'hc_pickleball_court2')).toEqual(['A', 'B']);
});

test('倒计时到期：默认执行 A，声望 -5，日志写明原因', () => {
  const s = runFor(openCard(fixture('hc_start', { cash: 400, reputation: 50 }), 'hc_pickleball_court2'), days(2));
  expect(s.facilities.court_2.state).toBe('rented_pickleball');
  expect(s.stats.reputation).toBe(45);
  expect(lastLog(s).cause).toEqual({ card: 'hc_pickleball_court2', option: 'default' });
});

test('选 B：3 天后出现社区群吐槽，因果链指向 B', () => {
  const s = runFor(choose(openCard(fixture('hc_start'), 'hc_pickleball_court2'), 'B'), days(3));
  expect(openCards(s)).toContain('hc_pickleball_rant');
  expect(causeChain(s, 'hc_pickleball_rant')).toContain('hc_pickleball_court2:B');
});
```

### 内容校验（构建时）

技术文档已列出的检查照做：schema、引用存在、只读不写的标记、倒计时卡必须有默认后果、两个选项效果完全相同。测试上再补三条：

- **可达性检查。** 静态分析每张卡的前置条件，用到的状态量取值范围里是否存在能满足它的组合；不可能满足的直接报错。
- **文案完整性。** 每个文案键在 zh 和 en 里都存在；缺失时开发版显示醒目的占位符，不能显示空白。
- **锚点完整性。** 内容里引用的锚点名（如 `court_2`、`court.feed_spot`）在对应场景模块的 `anchors` 里都存在，导航图是连通的。

## 机器人跑局与数值平衡

模拟不依赖画面，所以可以在命令行里让不同性格的机器人各跑上千局，用统计结果发现单元测试发现不了的问题：卡死、永远不出现的卡、绝对正确的选项、太简单或太难。

### 机器人类型

每种机器人代表一种玩家，或者一种极端打法。它们的通关率之间的差距，就是"决策有没有意义"的度量。

| 机器人 | 打法 | 用来发现 |
| --- | --- | --- |
| 随机型 | 每张卡随机选项，总监随机走动 | 基线：乱玩也能通关说明太简单 |
| 贪心型 | 每次选当下现金或质量收益最大的选项 | 短期最优是否等于长期最优（不应该） |
| 声望型 | 优先声望和社区关系 | 不同策略是否都有通关路线 |
| 摆烂型 | 从不处理任何卡，全部等倒计时到期 | 默认后果是否真的有代价 |
| 宅总监 | 总监从不移动 | 总监走位是否真的重要 |
| 搜索型 | 在关键卡上枚举全部选项各跑 100 局 | 某个选项是否在所有情况下都更好 |

### 统计指标与建议阈值

阈值是建议初值，第一批数据跑出来后由策划校准，写进 `sim-cli` 的配置文件。

| 指标 | 怎么算 | 建议阈值 | 越线说明 |
| --- | --- | --- | --- |
| 每幕通关率 | 按机器人分别统计 | 随机型 < 30%，贪心型 < 70%，摆烂型 = 0% | 太简单，或倒计时没有代价 |
| 卡覆盖率 | 1000 局里每张卡至少出现几次 | 每张卡 ≥ 1 次；垂直切片的里程碑卡 100% | 前置条件写错或不可达 |
| 软锁 | 没有卡可发、没有活动、离里程碑也没有进展，持续若干游戏日 | 0 局 | 状态卡死，玩家只能干等 |
| 支配选项 | 搜索型：某选项在所有起始状态下通关率都最高 | 关键卡上不存在 | 违反"有趣的选择" |
| 状态量健康 | 每 tick 检查 | 无 NaN、无越界 | 效果或公式有错 |
| 压力曲线 | 导演压力值随时间的序列 | 无过长平坦段，无连续危机（时长待定） | 兴趣曲线不对 |
| 一幕时长 | 通关局的游戏内天数分布 | 待游戏日长度确定后再定 | 节奏太拖或太赶 |

### 运行方式

```bash
pnpm sim run --act hollow_creek --bot greedy --runs 1000 --seeds 1-1000 --director steady
pnpm sim report --compare baseline   # 和上一次基线对比，变化超过阈值标红
```

报告输出为 JSON 和一张 HTML 页面。每晚跑一次全部机器人，结果和前一晚对比。任何越线的局都附带种子和命令日志，开发者可以在浏览器里直接重放那一局。

## 集成与端到端测试

这一层验证各部分拼在一起后仍然守住技术文档的六条原则，尤其是"确定性"和"结果先于演出"。大部分检查都归结为一句话：两种跑法最后的状态哈希必须相同。

### 确定性与回放

| 检查 | 做法 | 通过标准 |
| --- | --- | --- |
| 重放一致 | 同一种子 + 同一命令日志跑两遍 | 状态哈希相同 |
| 变速一致 | 同一局分别用 1×、2×、中途多次暂停跑完 | 状态哈希相同 |
| 存读档一致 | 在任意 tick 存档、读档再继续，对比一口气跑完 | 状态哈希相同 |
| 有无画面一致 | 同一局在浏览器里带渲染跑，和在命令行无头跑 | 状态哈希相同；不同说明渲染层偷偷改了状态 |
| 跨浏览器一致 | 同一局在 Chromium、Firefox、WebKit 各跑一遍 | 状态哈希相同 |
| 回放集 | 每修一个 bug，把复现它的存档和命令日志加入回放集 | 回放集全部通过 |

跨浏览器一致这一条要提前注意：`Math.sin`、`Math.exp` 这类函数在不同 JS 引擎里末位可能不同。模拟里尽量不用它们，必须用时换成自己实现的版本，否则回放和 bug 复现会在别的浏览器上失效。

### 存档与迁移

- 维护一个旧存档样本库 `fixtures/saves/`，每个存档格式版本至少一份，覆盖三幕各一个时间点。每次构建都把全部样本升级到最新版本并跑 schema 校验。
- 自动存档的三个时机都要测到：事件卡结算后、每幕开始时、页面隐藏时。
- 异常情况：存档写到一半关闭页面、IndexedDB 不可用（如私密模式）、导入被手改坏的 JSON。期望是不崩溃、不覆盖好存档、给出明确提示。

### 跨幕继承

准备一组测试用的 `Legacy`，可以直接从第二幕或第三幕开始玩，不用每次从头打。重点检查：

- 随行名额和取舍生效；忠诚度低的人会拒绝跟随。
- 现金、设施、大部分会员不继承；声望按比例折算。
- 事件标记跨幕生效：例如第一幕当众开除 Dale，第三幕他以匹克球教练身份回来的事件能被触发。
- 留在 Hollow Creek 主持的人，决定后两幕里 Hollow Creek 以什么事件出场。

### 模拟与表现的一致性

- **演出和结果一致。** 测试模式下，表现层把实际演出的关键时刻（谁摔倒、谁赢了哪一分）上报出来，和模拟给出的结果逐条对比。
- **锚点对得上。** 每个场景加载后，内容里引用的每个锚点都能投影到画面内的有效位置；总监能沿导航图走到每个锚点。
- **自动暂停。** 重要事件卡出现时模拟发出暂停请求，界面暂停；设置里关闭后不暂停。

### 端到端冒烟（Playwright）

每个 PR 在预览链接上跑一条最短主流程：打开游戏 → 开除 Dale 卡出现 → 选一个选项 → 因果日志出现对应条目 → 2× 速度跑到下一张卡 → 存档 → 刷新页面 → 读档 → 状态与刷新前一致。

### 画面回归

每个场景四个相机角度截图，活动库每个活动截关键帧，和基准图做像素对比。另加一项旋转检查：相机连续转一圈，逐帧对比相邻帧，专门抓 Palm Oasis 那种几层地面高度相同导致的闪烁。

## 玩法测试（Playtest）

机器人能告诉你能不能通关，不能告诉你好不好玩。玩法测试从 M2 垂直切片开始，每两周一轮，每轮验证设计文档里的几条具体假设，而不是笼统地问"好玩吗"。

### 怎么组织

- **人数。** 每轮 5 名没玩过的新玩家，外加 1 到 2 名上一轮的回访玩家看变化。5 人通常已经能暴露大部分可用性问题。
- **人选。** 一半玩过经营游戏（Kairosoft、Two Point 类），一半没玩过。网球爱好者至少 1 人，检查网球细节是否可信。
- **过程。** 只给一句开场："你是这家网球俱乐部的新总监。"玩家边玩边说出想法，测试者只观察、不提示，卡住超过 2 分钟才介入并记录。
- **记录。** 录屏 + 调试面板导出的存档和命令日志。命令日志能精确还原玩家每一步，事后可以在任意时刻暂停回看。
- **结束后。** 5 分钟问卷 + 10 分钟访谈。

### 要验证的设计假设

| 设计假设 | 观察什么 | 建议通过标准 |
| --- | --- | --- |
| 第一幕让人感到"翻身" | 问卷："结束时你觉得俱乐部比开始时好了吗"；情绪最低点和最高点出现在哪里 | 多数人能说出一个"转折时刻" |
| 倒计时制造取舍，不制造焦虑 | 同时开着的卡数；过期卡里有多少是玩家故意放弃的；访谈中的"来不及"抱怨 | 过期卡多数是主动放弃，而不是没注意到 |
| 总监走位是决策，不是跑腿 | 玩家是否主动把总监派去关键地点；是否抱怨走路太慢 | 多数人至少一次为了某张卡主动移动总监 |
| 因果日志读得懂 | 事后挑一个延迟后果，让玩家解释原因 | 5 人中至少 3 人能说对 |
| 没有永远正确的选项 | 同一张卡在不同玩家间的选择分布；访谈"你犹豫过吗" | 关键卡上没有一个选项被所有人选 |
| 开除 Dale 能教会基本操作 | 第一次做决策用了多久；求助次数 | 无提示完成第一张卡 |
| 自动暂停不打断节奏 | 玩家是否手动关掉自动暂停；是否抱怨被打断 | 少于半数人觉得被打断 |

### 问卷（每次结束时）

1. 用一句话说说你刚才在做什么。（检查玩家是否理解目标）
2. 哪个决定最难做？为什么？（检查有趣的选择）
3. 有没有哪件事让你觉得"莫名其妙就发生了"？（检查因果日志）
4. 你最想再玩一次的原因，或者不想再玩的原因。
5. 1 到 5 分：节奏太慢 ↔ 太快；太简单 ↔ 太难。

每轮结束后整理成一页结论：哪些假设成立、哪些不成立、下一轮改什么。不成立的假设要么改设计，要么改假设本身，并同步回设计文档。

## 性能、兼容性与稳定性

性能预算沿用技术文档的建议初值。能稳定复现的指标（绘制调用数、加载体积）进 CI 自动卡；受机器影响大的指标（帧率）在固定的几台真机上定期测。

### 性能

| 指标 | 目标 | 怎么测 | 何时 |
| --- | --- | --- | --- |
| 帧率 | 集显笔记本 60 fps，移动端 30 fps | 固定场景、2× 速度、相机旋转一圈，记录 30 秒内的帧时间分布 | 每个里程碑，真机 |
| 每帧绘制调用 | 150 以内 | 每个场景加载完成后读渲染器统计 | 每个 PR |
| 首屏加载 | 3 秒以内（不含字体） | Playwright 限速网络下测量 | 每个 PR |
| 场景切换 | 2 秒以内 | 用测试 Legacy 触发换幕 | 每个里程碑 |
| 模拟速度 | 无头跑一局第一幕足够快，保证每晚的机器人跑局能跑完 | `sim-cli` 计时 | 每晚 |

### 兼容性

| 平台 | 浏览器 | 优先级 |
| --- | --- | --- |
| Windows / macOS 桌面 | Chrome、Edge | 必须 |
| macOS 桌面 | Safari、Firefox | 必须 |
| iOS | Safari | 目标平台确定后再定 |
| Android | Chrome | 目标平台确定后再定 |

另外两项：WebGL 不可用时给出明确提示而不是白屏；画质档位（像素化程度、阴影、环境动画）在低端设备上能把帧率拉回目标。

### 稳定性

- **长时间运行。** 机器人在浏览器里 2× 速度连续玩 2 小时，内存不持续增长，帧率不衰减。
- **页面生命周期。** 切换标签页、最小化、合上笔记本再打开：自动存档触发，回来后时钟不会因为后台时间而跳跃。
- **本地化。** zh 和 en 两种语言下截图事件卡、HUD、因果日志，检查长文本不溢出、不截断。

## 缺陷管理与测试节奏

每个 bug 都必须能一键复现，修好后变成一条永久的回放测试。确定性设计让这件事几乎没有成本：种子加命令日志就是完整的复现步骤。

> 图：测试节奏 · 4 档，每档一个闸口（图只在在线文档里，见 README 的链接）

越靠左越快、越频繁；每一档都把问题挡在下一档之前。

### 缺陷报告

- **必带附件。** 调试面板一键导出"存档 + 命令日志 + 种子 + 内容版本"。没有这个附件的报告，先补附件再处理。
- **报告内容。** 版本或预览链接、现象、预期、截图或录屏、导出的附件。
- **修复流程。** 用附件在浏览器里重放复现 → 修复 → 把这份命令日志加入回放集 → 合并。同一个 bug 不会悄悄回来。

### 严重级别

| 级别 | 定义 | 例子 | 处理 |
| --- | --- | --- | --- |
| S1 | 崩溃、存档损坏、软锁 | 读档后白屏；没有卡可发也到不了里程碑 | 立即修，阻塞发布 |
| S2 | 规则或数值错误，卡永不触发，画面和结果不一致 | 倒计时到期没执行默认后果；动画里摔倒两次、结果里只有一次 | 当前迭代内修 |
| S3 | 画面错误 | 地面闪烁；名字标签错位 | 排期修 |
| S4 | 文案和小瑕疵 | 英文文案溢出事件卡 | 排期修 |

### 用调试面板手测

手测某张卡不用从头玩：用调试面板强制触发这张卡、改好需要的状态量、跳到下一个日历事件。查"这张卡为什么没出来"时，看面板里当前满足条件的卡和它们的权重。调试面板只在开发版和测试版里存在，正式版构建时整体剔除，发布前检查一次。

## 待定事项

下面几件事定下来之前，相关的阈值只能用建议初值：

- [ ] 一个游戏日对应多少现实时间：决定倒计时、软锁判定、一幕时长这些指标用什么时间单位。
- [ ] 各状态量的初始值和目标值：定了才能定机器人通关率的目标区间。
- [ ] 机器人通关率的目标区间：由策划在第一批跑局数据出来后拍板。
- [ ] 目标平台：决定移动端是否进入兼容性"必须"一栏。
- [ ] 是否要求跨浏览器结果一致：只做单机可以放宽；以后要做回放分享或云存档就必须保证。
- [ ] 玩法测试的玩家从哪里招：朋友圈、网球俱乐部、游戏社区各占多少。
- [ ] 是否收集遥测：目前是纯前端，玩法测试靠玩家手动导出存档和命令日志。
