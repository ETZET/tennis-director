# 网球总监 · 技术架构文档 v0.1

Oct 29, 2026 · @Enting

## 概述

结论：把现有的四个单文件原型拆成一个 TypeScript 工程，核心是一套不依赖画面的模拟引擎，画面和界面都只是它的订阅者，事件、活动、场景配置全部写成数据文件。这样加一张事件卡不用碰代码，加一幕只需要新增一个场景模块和一批数据。

玩法以 [网球总监 · 玩法设计文档 v0.1](https://claude.ai/artifact/L928nnUJivRPVhUzZXnrBi) 为准：三幕结构、事件驱动的即时时间、事件卡加倒计时、事件导演、总监走位、因果日志、跨幕继承。本文只讲怎么实现和怎么组织工程，不重复玩法规则。

### 现状

| 原型 | 对应 | 实现方式 |
| --- | --- | --- |
| [Hollow Creek Tennis Club](https://claude.ai/code/artifact/6081cc24-7752-4f7a-b0dc-3bdd71b91ed8) | 第一幕 | 单个 HTML，约 85 KB |
| [Maple Ridge Courts](https://claude.ai/code/artifact/b0988c55-1650-476e-b5ee-65ec51e9c85d) | 第二幕 | 单个 HTML |
| [Palm Oasis Racquet Club](https://claude.ai/code/artifact/42f3e857-86e8-46d4-8e4c-853543e772fe) | 第三幕 | 单个 HTML |
| [网球活动动画库](https://claude.ai/code/artifact/6061d9f4-4deb-4bcd-8d64-f7fd45c06718) | 训练、招生、比赛、团建 | 单个 HTML，带疲劳/天气/教练滑杆 |

四个原型的共同做法：从 CDN 加载 three.js r128，用代码程序化拼体素盒子再合并成大网格，用种子随机数（mulberry32）生成地形细节，HUD 是叠在画布上的 DOM，剧情写死在脚本的时间轴里。

这些做法里值得保留的是体素批处理器、场地坐标系（每块场地一个旋转的局部坐标系）、种子随机数和 HUD 的视觉风格。需要改掉的是：四份文件各自复制了一套工具代码；游戏状态散落在动画代码里；剧情和数值写死在脚本里，策划改不动。

### 本文范围

- 覆盖：技术选型、分层架构、目录结构、模拟核心、渲染、内容管线、存档、扩展方式、工程规范、迁移路线。
- 不覆盖：具体数值平衡、美术规范、音频、联网功能。

## 架构原则

六条原则，后面所有设计都从这里推出来。代码评审时如果某个改动违反其中一条，需要先写一条决策记录（ADR）说明理由。

1. **模拟和表现分离。** 模拟核心不引用 three.js，也不碰 DOM。同一套模拟可以在浏览器里跑，也可以在命令行里无头跑一千局做平衡测试。
2. **结果先于演出。** 一场训练、一场比赛的结果由模拟算出，动画只负责把这个结果演出来。动画永远不决定数值，否则存档、回放和测试都会失效。
3. **内容就是数据。** 事件卡、活动、场景初始状态、人物、特质、文案都是数据文件，经过 schema 校验。策划改数据不需要改代码。
4. **确定性。** 固定时间步长加种子随机数，加上玩家命令日志，就能完整复现一局。这是调试、回放、平衡测试和存档校验的基础。
5. **按名字引用，不按坐标。** 模拟只知道"1 号场""会所露台""停车场"这些锚点名字；锚点在三维空间的哪里，由场景模块决定。改场景布局不会影响事件和存档。
6. **状态是纯数据。** 游戏状态只包含可以序列化的普通对象，不放类实例、函数或 three.js 对象。存档就是把状态写下来。

## 技术选型

选型原则是继续用原型已经验证过的 three.js，只补上工程化需要的部分，不引入完整游戏引擎。经营模拟游戏的复杂度在规则和内容，不在渲染，所以要把投入放在模拟核心和内容工具上。

| 领域 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | TypeScript 7，strict 模式 | 事件卡、状态量、效果这类数据结构多，类型能挡住大部分低级错误；7.0 起编译器是原生实现，大约快 10 倍 |
| 构建与开发服务器 | Vite 8 | 热更新快；可以写插件在构建时校验内容数据 |
| 包管理 | pnpm workspaces | 用包边界强制分层，比如模拟包根本装不了 three |
| 3D 渲染 | three.js，npm 安装并锁定版本 | 原型已用；从 CDN 的 r128 升到当前稳定版（2026 年 9 月为 r186）；先用 WebGLRenderer，WebGPU 以后再评估 |
| 界面（HUD、事件卡、日志） | Preact + signals | 体积小，JSX 写界面比手拼 DOM 好维护；signals 适合订阅模拟状态 |
| 数据格式 | YAML 写，构建时编译成 JSON | 策划读写友好，支持注释；运行时只加载 JSON |
| 数据校验 | Zod | 同一份 schema 既生成 TypeScript 类型，又做运行时和构建时校验 |
| 测试 | Vitest；Playwright | Vitest 测模拟和内容；Playwright 做场景截图对比和冒烟测试 |
| 存档 | IndexedDB，外加导出为文件 | 浏览器本地存储，容量够；导出文件方便玩家备份和提交 bug |
| 本地化 | 键值文案表（zh、en） | 原型 HUD 是英文，设计文档是中文，从第一天起就不把文案写死在代码里 |
| 部署 | 静态托管（Cloudflare Pages、GitHub Pages 或 itch.io） | 纯前端，无服务器成本；每个 PR 自动出预览链接 |
| 以后上桌面 | Tauri 包装 | 网页版不改代码即可打包成 Steam 桌面版 |

刻意不选的：

- **完整游戏引擎（Unity、Godot 等）。** 网页是首发平台，three.js 原型已经可用，换引擎要重做全部美术。
- **Redux 等通用状态库。** 模拟状态由模拟核心自己管理，界面只读快照，不需要第二套状态管理。
- **ECS 框架。** 场上同时存在的实体只有几十个人和几块场地，普通的按 id 索引的对象表就够了，ECS 只会增加理解成本。

## 分层架构与目录结构

工程分成五个包，模拟核心在中间。表现层和界面层互不认识，都只读模拟的快照、只向模拟发命令。

> 图：分层架构 · 5 个包，依赖只朝模拟核心（图只在在线文档里，见 README 的链接）

点击场地让总监走过去，和在事件卡上选选项一样，都是一条命令；画面上发生的一切，都是模拟状态变化的结果。

### 目录结构

```text
tennis-director/
├─ packages/
│  ├─ shared/     类型、常量（层高表）、种子随机数、工具函数
│  ├─ sim/        模拟核心：时钟、状态、命令、系统、事件引擎、导演、存档迁移
│  ├─ content/    YAML 内容和 schema，构建时编译成 JSON
│  ├─ render/     three.js：voxel/ props/ scenes/ people/ choreo/ camera/
│  └─ ui/         Preact：HUD、事件卡、因果日志、调试面板
├─ apps/
│  ├─ game/       正式游戏入口，组装各包
│  ├─ sandbox/    活动动画库、场景查看器（现有原型迁到这里）
│  └─ sim-cli/    命令行无头跑局和平衡报告
├─ tools/         Vite 内容校验插件、截图对比脚本
├─ docs/adr/      架构决策记录
└─ CLAUDE.md      给 AI 协作者的架构规则
```

依赖方向只能往下：`apps` → `render` / `ui` → `sim` → `shared`。`content` 只由 `sim` 读取。`sandbox` 很重要：它让美术和动画可以脱离完整游戏单独开发和展示，现有的活动动画库原型就是它的第一版。

## 模拟核心

模拟核心是一个纯函数式的状态机：输入是当前状态和玩家命令，输出是新状态和一串领域事件。它位于 `packages/sim`，不依赖任何浏览器 API。

### 时钟

- **固定步长。** 一个 tick 代表固定的游戏内时长（建议 1 游戏分钟，待玩法确定一天的现实时长后再定）。渲染帧率和模拟步长无关，渲染在两个 tick 之间插值。
- **变速只改每秒跑几个 tick。** 暂停、1×、2× 都是同一套逻辑，不会因为变速产生不同结果。
- **自动暂停是模拟发出的信号。** 重要事件卡出现时，模拟发出 `requestPause` 事件，由外层决定是否暂停（设置里可以关）。

### 状态

`GameState` 是一个可以直接 `JSON.stringify` 的对象，按 id 归一化：

```ts
interface GameState {
  version: number;            // 存档格式版本
  act: 'hollow_creek' | 'maple_ridge' | 'palm_oasis';
  clock: { day: number; minute: number; speed: 0 | 1 | 2 };
  rng: RngState;              // 随机数也是状态的一部分
  stats: Record<StatId, number>;           // 资金、声望、质量、出售倒计时……
  people: Record<PersonId, Person>;        // 球员、教练、员工，各带士气/疲劳/技术/特质
  facilities: Record<FacilityId, Facility>;// 场地、气膜、泳池
  director: { at: AnchorId; path: AnchorId[]; busyUntil?: number };
  cards: { open: OpenCard[]; cooldowns: Record<CardId, number> };
  activities: RunningActivity[];
  flags: Record<string, boolean | number | string>; // 事件记忆，如 dale_fired_publicly
  log: CausalEntry[];         // 因果日志
}
```

状态量（`stats`）不写死在类型里，而是在数据里注册：每个状态量有 id、取值范围、显示方式和所属的幕。第二幕的"学业资格"、第三幕的五条利益方满意度，都是注册出来的，不需要改核心代码。

### 命令

玩家的所有操作都是命令对象，例如 `{ type: 'chooseOption', card: 'hc_pickleball_court2', option: 'C' }`、`{ type: 'assign', person: 'director', target: 'c1_upkeep' }`（ADR 0012）、`{ type: 'setSpeed', speed: 2 }`。命令先校验，再执行，执行结果追加到命令日志。初始种子加命令日志就能完整重放一局。

### 每个 tick 的系统顺序

系统是按固定顺序执行的函数，每个只负责一件事：

1. **日历系统**：推进时间，触发日历事件（比赛日、董事会、考试周）。
2. **总监系统**：总监沿锚点路径移动；到达后解锁"需要亲临"的选项，并给附近的人加"在场"修正。
3. **活动系统**：推进进行中的活动，到时结算结果。
4. **人员系统**：疲劳恢复、士气漂移、受伤判定。
5. **经济系统**：按周结算收支。
6. **事件系统**：倒计时减少，过期的执行默认后果；评估阈值事件的前置条件。
7. **导演系统**：计算压力值，决定这一刻要不要发新卡、发哪类卡。

### 事件引擎

事件卡采用 storylet 模型：引擎每隔一段时间筛出所有前置条件满足、不在冷却中的卡，再按权重抽取。

- **前置条件是数据，不是代码。** 用一个小的条件语言表达，例如 `all: [{stat: cash, lt: 500}, {facility: court_2, is: idle}]`。引擎负责解析和求值，这样条件可以被校验、被工具读懂。
- **效果是白名单操作。** 选项的效果只能用注册过的操作：改状态量、设标记、开始活动、安排后续事件、改关系、移动人员等。确实需要特殊逻辑时，在代码里注册一个具名钩子，数据里按名字调用。
- **每个效果都带原因。** 效果执行时记录"来自哪张卡的哪个选项"，写进因果日志。延迟后续事件也带着原因链，玩家看到的就是"因为你拒绝了匹克球，所以他们在社区群吐槽"。

### 事件导演

导演是一个可配置的函数，读取压力指标（现金、未处理卡数、连败次数等，具体由数据定义），输出对各类卡的权重修正和发卡间隔。设计文档里的"稳健型、戏剧型、随机型"就是三份不同的导演配置文件，不是三套代码。

### 活动结算

活动（训练、招生、比赛、团建）分两半：模拟这半根据疲劳、天气、教练水平和随机数算出结果，例如"体力 −12、技术 +3、出现 1 次失误摔倒"；渲染那半拿到结果后播放对应的动画。结果里包含演出需要的关键时刻（谁赢了哪一分、谁摔倒了），动画按这些时刻编排，保证画面和数值一致。

## 表现层

表现层把模拟状态画出来，并把模拟发出的领域事件演出来。它只读模拟的快照，唯一能影响模拟的方式是发命令。

### 体素构建

- **保留程序化建模。** 原型里的体素批处理器（逐个加盒子、按材质合并成一个网格）抽成 `render/voxel` 模块，四个场景共用一份。场景地形和建筑继续用代码拼，好处是可以版本管理、可以评审、可以参数化。
- **道具做成预制件。** 球网、长椅、灯柱、气膜、匹克球网这类反复出现的东西，写成返回几何体的函数，放在道具库里。复杂道具以后可以从 MagicaVoxel 的 `.vox` 文件导入，接口不变。
- **静态和动态分开。** 地形、建筑这类静态体素在场景加载时一次性合并；人物、球、飘字这类动态物体单独管理，数量多的（比如观众）用 `InstancedMesh`。
- **层高表是全局常量。** Palm Oasis 的旋转闪烁问题，根源是几层地面高度相同。把各层地面高度集中写在一张表里，所有场景只能引用这张表，从根上避免同类问题：

```ts
export const LAYER = {
  ground: 0, lawn: 0.02, path: 0.04, court: 0.06,
  lines: 0.08, shadow: 0.10, lightPool: 0.12,
} as const; // 相邻两层至少相差 2 cm
```

### 场景模块

每一幕是一个场景模块，统一接口：

```ts
export default defineScene({
  id: 'hollow_creek',
  build(ctx) { /* 用体素构建器拼地形、场地、会所 */ },
  anchors: { court_1: …, court_2: …, deck: …, lot: …, creek_bridge: … },
  navGraph: [ ['deck', 'stairs_upper'], ['stairs_upper', 'court_1'], … ],
  cameraPresets: { overview: …, court_1: … },
  ambient: [ /* 乌鸦、下雨、泳池落叶等环境动画 */ ],
});
```

锚点和导航图同时被模拟和渲染使用：模拟用导航图算总监走到某处要多久，渲染用锚点的三维坐标让小人真正走过去。原型里每块场地一个旋转坐标系的做法保留，挂在锚点上。

### 人物与活动演出

- **人物沿用原型的体素小人和程序化动画**（走、跑、挥拍、坐地上、刷手机），外观由数据决定：肤色、发型、服装配色、身高。
- **活动演出由原子动作编排。** 活动库里的动作拆成原子步骤：走到锚点、对拉、发球、摔倒、表情气泡、弹出数字、彩带。一个活动的演出就是这些步骤的时间线，按模拟给的结果填参数。
- **通用活动加场景定制。** 演出只引用锚点名字，比如"教练站在 `court.feed_spot`"。同一个训练活动放到不同场景，自动用那个场景的锚点。需要特别定制时，场景可以覆盖某个活动的演出。

### 相机与界面叠层

- 正交相机、有限角度旋转、缩放、跟随剧情，和原型一致；参数由场景的相机预设提供。
- 名字标签和对话气泡继续用 DOM 叠层，按锚点或人物位置每帧投影，由界面层负责。
- 像素化程度（原型里的 Pixels 开关）做成画质设置，同时用来照顾低端设备。

### 性能预算（建议初值，用实测校准）

| 指标 | 目标 |
| --- | --- |
| 帧率 | 主流集显笔记本 60 fps，移动端 30 fps |
| 每帧绘制调用 | 150 以内 |
| 首屏加载 | 3 秒以内（不含字体） |
| 场景切换 | 2 秒以内，期间显示过场 |

## 内容管线

所有游戏内容都放在 `packages/content`，用 YAML 编写，构建时校验并编译成 JSON。设计文档里的事件卡规格表，直接对应下面的 schema。

### 内容类型

| 类型 | 位置 | 一个文件包含 |
| --- | --- | --- |
| 事件卡 | `events/<幕>/<id>.yaml` | 一张卡 |
| 活动 | `activities/<id>.yaml` | 输入变量、结果公式、调用哪个演出 |
| 状态量 | `stats.yaml` | 全部状态量的注册表 |
| 人物与特质 | `people/*.yaml`、`traits.yaml` | 初始人物、特质修正 |
| 场景配置 | `acts/<幕>.yaml` | 初始状态、胜负条件、里程碑卡、导演配置 |
| 导演配置 | `directors/*.yaml` | 稳健型、戏剧型、随机型 |
| 文案 | `i18n/zh.yaml`、`i18n/en.yaml` | 所有显示文字 |

### 示例：匹克球租场卡

```yaml
id: hc_pickleball_court2
act: hollow_creek
source: threshold
when:
  all:
    - { stat: cash, lt: 500 }
    - { facility: court_2, is: idle }
weight: 3
cooldown: 7d
countdown: 2d
stage: { anchor: court_2, activity: pickleball_meetup }
options:
  A:
    effects:
      - { stat: weekly_income, add: 300 }
      - { facility: court_2, set: rented_pickleball }
      - { flag: members_grumble_identity, set: true }
  B:
    effects:
      - { schedule: hc_pickleball_rant, in: 3d }
  C:
    requiresDirectorAt: court_2
    check: { stat: reputation, vs: 40 }
    onSuccess:
      - { stat: weekly_income, add: 150 }
      - { unlockActivity: pickleball_friendly }
    onFail:
      - { schedule: hc_pickleball_rant, in: 1d }
default:
  then: A
  extra:
    - { stat: reputation, add: -5 }
text: events.hc_pickleball_court2   # 标题、描述、选项文字都在 i18n 里
```

### 构建时校验

一个 Vite 插件在开发和构建时检查全部内容，出错直接在浏览器里显示错误浮层：

- 字段类型和必填项符合 schema。
- 所有引用都存在：后续事件 id、活动 id、锚点名、状态量 id、文案键。
- 标记只被读、从未被写（多半是拼错了），给出警告。
- 每张卡至少有一个选项，倒计时卡必须有默认后果。
- 两个选项效果完全相同，给出警告（违反"有趣的选择"）。

### 热更新与调试

开发模式下改 YAML，游戏不重启就加载新内容。配合调试面板，可以直接强制触发某张卡、修改状态量、跳过时间，策划改一张卡几秒钟就能看到效果。

## 存档与版本迁移

存档就是带版本号的状态快照；每次存档格式变化都配一个迁移函数，旧存档读进来时逐级升级到最新版本。

- **存什么。** 版本号、内容版本、种子、完整 `GameState`，以及最近一段命令日志（用于复现 bug）。
- **存在哪。** IndexedDB 保存多个存档位；支持导出和导入 JSON 文件。
- **何时自动存。** 每次事件卡结算后、每幕开始时、页面隐藏时（切换标签页、关闭浏览器）。
- **迁移。** `sim/migrations/` 下按编号放迁移函数，例如 `0004_add_stakeholders.ts`。每个迁移都配一个旧版本存档样本做测试。
- **内容 id 不改名。** 事件卡、人物、标记的 id 一旦上线就不再改；要废弃就标记为 deprecated，迁移函数负责把旧 id 映射到新 id。

### 跨幕继承也是一次迁移

设计文档里的"谁跟我走"事件，技术上是一个显式函数：`carryOver(state, choices) → Legacy`。`Legacy` 是一个独立的、有版本号的数据结构，只包含允许继承的东西：总监等级和特质、选中人员、关系、事件标记、折算后的声望。下一幕用 `Legacy` 加上该幕的初始配置生成新状态。

这样做的好处是：继承规则集中在一个函数里，方便调整比例；也支持"从第二幕开始玩"这类调试和关卡选择功能，只要准备一份测试用的 `Legacy` 即可。

## 扩展点

扩展是否容易，看加一样新东西要改几个地方。目标是大部分扩展只加文件、不改已有文件，核心代码只在新增"一类"东西时才动。

| 想加什么 | 改哪里 | 要写代码吗 |
| --- | --- | --- |
| 一张事件卡 | 新增 `events/<幕>/<id>.yaml` 和文案 | 不用 |
| 一个特质（如"大心脏"） | `traits.yaml` 加一条修正 | 不用 |
| 一个状态量（如"媒体关注度"） | `stats.yaml` 注册，HUD 配置里决定是否显示 | 不用 |
| 一种导演风格 | `directors/` 新增配置 | 不用 |
| 一种新活动 | 活动 YAML（输入、结果公式）+ 用原子动作写一段演出 | 少量，只写演出编排 |
| 一种新原子动作（如"抛彩带"） | `render/choreo/` 注册一个动作 | 是 |
| 一种新效果类型（如"转会"） | `sim/effects/` 注册函数和 schema | 是，校验器自动识别 |
| 一个新场景或新的一幕 | 新场景模块（建模、锚点、导航图）+ `acts/<幕>.yaml` + 一批事件卡 | 只写场景建模 |
| 一个新平台（Steam、移动端） | 换平台适配层（存档、输入、窗口） | 是，但不碰模拟和内容 |

实现方式是注册表：效果、条件、原子动作、场景、活动演出都有各自的注册表。核心代码只按名字查表，不知道具体有哪些。新增一类东西就是往表里注册一项，校验器、调试面板、存档都会自动认识它。

## 工程实践

事件驱动的经营游戏最容易出的问题是：内容越来越多以后，卡与卡之间的组合没人能全部手测。所以测试重点放在模拟和内容上，用机器人自动跑局，而不是只靠人玩。

### 测试分四层

| 层 | 测什么 | 工具 | 何时跑 |
| --- | --- | --- | --- |
| 单元测试 | 条件求值、效果执行、倒计时、导演、迁移函数 | Vitest | 每次提交 |
| 确定性测试 | 同一种子加同一命令日志，跑完后状态哈希必须一致 | Vitest | 每次提交 |
| 机器人跑局 | 随机型、贪心型等几种机器人各跑上千局，统计每幕通关率、平均时长、从未出现的卡、卡死的状态 | `apps/sim-cli` | 每晚，或内容改动后 |
| 画面回归 | 每个场景四个角度截图，和基准图对比；活动库每个活动截关键帧 | Playwright | 每个 PR |

机器人跑局的报告就是平衡工具：比如"第一幕贪心机器人通关率 92%"说明太简单，"`hc_developer_visit` 在 1000 局里从未出现"说明前置条件写错了。

### 持续集成

每个 PR 自动执行：类型检查、代码规范、单元测试、内容校验、构建、画面回归，然后部署一个预览链接。主分支合并后自动部署测试版。

### 调试工具

开发版内置一个调试面板（快捷键打开）：

- 查看和修改任意状态量、人物属性、标记。
- 强制触发某张卡，列出当前满足条件的所有卡和它们的权重。
- 时间快进、跳到下一个日历事件。
- 显示当前种子；一键导出"存档加命令日志"，用于提交 bug 后精确复现。
- 帧率、绘制调用数、内存的实时显示。

### 协作规范

- **分层由工具强制。** `sim` 包的依赖里没有 three 和 Preact；另外用依赖检查规则禁止 `render` 和 `ui` 互相直接引用，二者只通过模拟快照和命令沟通。
- **重要决策写 ADR。** `docs/adr/` 下一份决策一个文件，例如"为什么不用 ECS""为什么内容用 YAML"。
- **提交信息用 Conventional Commits**，方便自动生成更新日志。
- **给 AI 协作者一份架构说明。** 原型主要是和 Claude 一起做的，以后也会。仓库根目录放一份 `CLAUDE.md`，写明分层规则、目录约定、注册表用法和"不要做的事"，AI 生成的代码就会遵守同样的边界。文件保持小而单一职责，也更方便 AI 和人一起改。

## 迁移路线

先把现有原型搬进新工程且画面不变，再建模拟核心，然后用第一幕前 15 分钟的垂直切片验证玩法。切片通过之前，不开始第二、三幕的内容生产。

> 图：迁移路线 · 6 个阶段，每个带一个闸口（图只在在线文档里，见 README 的链接）

M2 是整条路线的关键：如果"事件加倒计时加总监走位"不好玩，在这里发现只需要改模拟和数据，成本最低。

M0 的具体做法：先把 Hollow Creek 原样拆进 `render`（体素批处理器、场地坐标系、地形、人物），写死的剧情时间轴暂时保留在 `sandbox` 里当演示；然后单独一步升级 three.js，对照四个角度的截图调光照。另外两个场景和活动库用同样的方法迁移，可以和 M1 并行。

## 风险与待定事项

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 把原型代码整段复制进新工程 | 四份重复工具代码和写死的剧情变成长期债务 | 迁移时只抽取，不复制；用截图对比保证画面不变 |
| 动画逻辑里偷偷改数值 | 存档、回放、测试全部失效 | 依赖规则禁止 `render` 写状态；确定性测试兜底 |
| 事件卡数量增长后组合爆炸 | 出现卡死、永远不触发的卡、数值失控 | 内容校验加机器人跑局，每晚出报告 |
| three.js 从 r128 升到当前版本 | 色彩管理、光照强度单位等默认行为变了，画面会偏色偏暗 | 迁移第一步单独做升级，对照截图调光照；之后锁版本，按季度评估升级 |
| 移动端性能不足 | 帧率低、发热 | 画质档位（像素化程度、阴影、环境动画）；性能预算进 CI |
| 存档格式频繁变动 | 测试玩家的存档失效 | 从第一个版本起就写迁移函数，不等正式发布 |

待定事项（会影响技术决策）：

- [ ] 一个游戏日对应多少现实时间：决定 tick 长度和倒计时的显示方式。
- [ ] 目标平台：只做网页，还是之后上 Steam 或移动端。影响输入设计和是否尽早做平台适配层。
- [ ] 是否需要云存档或账号：需要的话要加后端，目前方案是纯前端。
- [ ] 团队规模和分工：如果有专职策划，内容工具（比如事件卡可视化编辑器）的优先级要提前。
- [ ] 是否做 Mod 支持：内容已经是数据，开放加载外部内容包的成本不高，但要尽早定安全边界。
