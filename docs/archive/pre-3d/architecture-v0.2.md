## 概述

网球总监是一个 TypeScript monorepo：核心是一套不依赖画面的模拟引擎，画面（`@td/iso`，Canvas 2D 等距像素）和界面（Preact）都只是它的订阅者；地图、设施、岗位、工单、事件卡、人物、文案全部是数据文件。加一张卡、调一个数不用碰代码；加一张地图只需要一个实现 `Site` 接口的场景模块和一份地图数据。

玩法以 [玩法设计文档 v0.5](game-design-v0.5.md) 为准，测试以 [测试文档 v0.2](testing-v0.2.md) 为准，具体决策在 `docs/adr/`。本文只讲怎么实现、怎么组织工程，不重复玩法规则。和 ADR 冲突时以 ADR 为准。

### 现状（2026-11-03）

- 整局只有一张地图：Indian Wells 的 Palm Oasis Racquet Club，开局荒了十年（ADR 0016、0018）。
- 核心玩法是"招人 + 把人拖到地点上的岗位和工单"（ADR 0012–0015）。事件卡是偶发的点缀。
- 画面是 `packages/iso`：Canvas 2D 软件光栅的 2.5D 等距像素（ADR 0019），照美术样片 `docs/art/style-demos/isometric-2.5d/` 做。原来的 three.js 体素包 `packages/render` 和 Hollow Creek 场景已经删掉，仓库里不再有 three。

### 本文范围

- 覆盖：架构原则、技术选型、分层和目录、模拟核心、表现层、界面、内容管线、存档、扩展方式、工程实践、风险。
- 不覆盖：数值平衡（见设计文档和 `docs/balance/`）、美术规范、音频、联网。

## 架构原则

六条原则。代码评审时如果某个改动违反其中一条，需要先写一条 ADR 说明理由。

1. **模拟和表现分离。** 模拟核心不引用画面包，也不碰 DOM。同一套模拟可以在浏览器里跑，也可以在命令行里无头跑几百局做平衡。
2. **结果先于演出。** 岗位转一圈的收益、工单的进度、表演赛的成败都由模拟算出，动画只负责演。动画永远不决定数值，否则存档、回放和测试都会失效。
3. **内容就是数据。** 地图、设施、岗位、工单、事件卡、人物、特质、文案都是 YAML，经过 schema 校验。策划改数据不需要改代码。
4. **确定性。** 固定步长（1 游戏分钟）加种子随机数，加上玩家命令日志，就能完整复现一局。这是调试、回放、平衡测试和存档校验的基础。
5. **按名字引用，不按坐标。** 模拟只知道"外场 1""会所""大门"这些锚点名字和步行分钟数；锚点在世界坐标的哪里、路怎么走，由 `Site` 决定。改布局不影响事件和存档。
6. **状态是纯数据。** 游戏状态只包含可以序列化的普通对象，不放类实例、函数或场景图节点。存档就是把状态写下来。

## 技术选型

画面是自己写的 Canvas 2D 软件光栅（ADR 0019），不用 WebGL、不引入游戏引擎。经营模拟的复杂度在规则和内容，不在渲染。

| 领域 | 选择 | 现状 |
| --- | --- | --- |
| 语言 | TypeScript 7，strict | 用着 |
| 构建与开发服务器 | Vite 8；内容插件做热更新和校验 | 用着 |
| 包管理 | pnpm 10 workspaces；Node 22 | 用着 |
| 画面 | `@td/iso`：Canvas 2D 软件光栅的 2.5D 等距像素，轻量场景图，字符画素材 | 用着；不依赖任何渲染库 |
| 界面 | Preact（HUD、事件卡、员工条、地点清单、调试面板），读模拟快照 | 用着；没有用 signals，每 0.2 秒和每次事件重绘一次快照 |
| 数据格式 | YAML 写，构建时编译成 JSON（`src/generated/content.json`） | 用着 |
| 数据校验 | Zod 4 | 用着 |
| 规范 | Biome（格式和规范）、dependency-cruiser（分层） | 用着 |
| 测试 | Vitest；Playwright（无头 Chromium，用于试玩桥和截图） | 用着；画面回归随 ADR 0019 全部重拍，待重建 |
| 存档 | IndexedDB 自动存档，加导出 JSON | 用着 |
| 本地化 | 键值文案表（zh 默认，en 用 `?lang=en`） | 用着 |
| 部署 | 静态托管；现在用 claude.ai 预览页 | 正式托管待定 |

刻意不选的：完整游戏引擎（换引擎要重做全部美术）；Redux 等通用状态库（模拟自己管状态，界面只读快照）；ECS（场上只有几十个人和十几块场地，按 id 索引的对象表就够）。

## 模拟核心（`packages/sim`）

模拟是一个状态机：输入当前状态和玩家命令，输出新状态和一串领域事件。不依赖任何浏览器 API。

### 时钟

- **一个 tick = 1 游戏分钟。** 营业时间 8:00–20:00；收盘时结算这一天，然后直接跳到第二天开门（夜里不模拟，走在路上的人直接到）。
- **变速只改每秒跑几个 tick**（`apps/game/src/session.ts`）。1× 下一个营业日约 2 分钟真实时间；所有有需求的岗位都有人、又没有工单在做时自动加速。暂停、变速不会改变结果。
- **自动暂停是模拟发出的信号**：重要的卡打开时发 `requestPause`，由外层决定暂停。

### 状态（`state.ts`，存档版本 6）

`GameState` 可以直接 `JSON.stringify`，按 id 归一化。主要字段：

| 字段 | 内容 |
| --- | --- |
| `t`、`rng`、`seed` | 绝对游戏分钟、随机数状态、种子 |
| `act`、`directorConfig` | 地图配置 id（只有 `indian_wells`）、导演配置 |
| `stats` | 状态量（现金、声望、质量、会员、服务率、复原），在 `stats.yaml` 注册 |
| `facilities`、`condition` | 每个设施的当前状态、状况 0–100 |
| `people` | 每个人：是否在职、站在哪个锚点、三项能力和球技（`play`）、士气、疲劳、手上的岗位或工单（`job`）、走路（`walk`）、办事（`errand`）、习惯（`routine`）、暂停的工单（`resume`） |
| `headCoach` | 主教练 |
| `posts`、`orders`、`orderLog` | 持续岗位这一圈的进度；开了工的工单；工单的冷却和完成次数 |
| `week`、`ledger` | 本周需求和服务分钟；今天每个岗位的账（收盘时合成一条因果日志） |
| `cards` | 开着的卡、排上日程的卡、冷却、出现次数、导演下次抽卡时间 |
| `activities` | 进行中的活动 |
| `season`、`weather`、`flags` | 季节、今天的天气、事件记忆 |
| `log` | 因果日志（每条带原因和引出它的上一条） |
| `outcome` | 结局 |

`World`（`world.ts`）是内容的索引：按 id 建好的表、预编译的表达式、导航图。它从内容包和地图 id 算出来，有缓存，不进存档。

### 命令（`game.ts`）

玩家的所有操作都是命令对象：`chooseOption`（选卡）、`assign`（把一个人拖到岗位或工单上，`null` 是叫停），以及调试用的 `debugSetStat`、`debugSetFlag`、`debugForceCard`、`debugSkip`。命令先校验（例如 `canAssign`），再执行，接受的命令带时间戳写进命令日志。种子加命令日志就能完整重放一局（`replay`）。

### 每个 tick 的顺序（`systems.ts`）

1. **日程**：到点的日历卡和后续卡打开。
2. **人员**（`staff.ts`）：办事到时结束 → 每 10 分钟按习惯换班 → 持续岗位转圈（时段里、有人、到场才转；每圈结算效果、磨损或修复设施、总监涨能力）→ 工单推进（第一个人到场扣材料费；按每个人的速度加进度；做满就结算）。
3. **活动**：到点的活动开始、结束的结算。
4. **质量**：每 10 分钟向目标表达式靠近一步。
5. **事件**：倒计时到期的卡执行默认后果。
6. **导演**：到了抽卡时间，按压力值调权重抽一张。
7. 时间 +1 分钟 → **走路**：走到了就到达，开始干活。

**收盘**：今天的岗位账写进因果日志 → 设施按 `decay_day × 季节倍数` 衰减 → 经济（会费 + 设施收入 − 维护费 − 工资，按天折算）、会员和声望漂移（周日才动）、员工特质 → 周日结算服务率 → 重算派生量（服务率、复原）→ 检查失败条件 → 换季、抽今天的天气。

### 岗位、工单、走路（ADR 0012–0015）

- 岗位和工单都挂在地点上（`at`）。岗位有技能、一圈的时长、时段和星期、存在条件（`when`，例如设施修好了）、每圈效果、磨损和修复；工单有技能、工作量、材料费、人数上限、出现条件、只做一次、冷却、修复量、判定、效果。
- 速度 = `0.5 + 能力/100`（能力 50 是 1 倍）。中途拉走持续岗位：这一圈作废，已算的服务分钟退回去，发 `postInterrupted`；工单进度保留。
- 走路按导航图走最短路（`walk.ts`），固定速度；到了才开始干。Indian Wells 的导航图两两相连，分钟数由画面步道的长度换算，测试保证两边一致。
- 习惯（ADR 0014）：玩家亲手派过的岗位记在这个人身上，岗位关门或闲着时自己走去下一个。

### 事件引擎（`cards.ts`、`effects.ts`、`vars.ts`）

- **storylet 模型：** 阈值卡和随机卡由导演每隔一段时间筛出所有满足条件、不在冷却中、没超过出现次数的卡，按权重抽一张；里程碑、日历、后续卡按时间表打开。
- **条件是数据**（`all` / `any` / `not` / 状态量 / 标记 / 设施 / 天气 / 季节 / 表达式……），**效果是白名单操作**：改状态量、设标记、改设施状态、改设施状况、安排后续卡、开始活动、招人、开人、改人的属性、派人办事、写一行日志、结束这一局。每个效果都可以带条件和概率。
- **表达式语言**（`packages/shared/src/expr.ts`）：编译时检查语法和变量名；能读的变量和内容编译器的 `COMPUTED_VARS` 一一对应（例如 `stat.cash`、`condition.outer_1`、`restored`、`worker.skill`）。
- **每个效果都带原因**写进因果日志；后续卡带着引出它的日志条目，玩家能看到"因为……所以……"。

### 导演

导演是一份配置（`directors/*.yaml`）：抽卡间隔、同时最多开几张、两张卡之间的最小间隔、压力表达式（现金、未处理的卡、质量）、按语气的权重表达式。稳健型、戏剧型、随机型是三份配置，不是三套代码。Indian Wells 用稳健型。

### 机器人（`bots.ts`）

贪心型、谨慎型（不招人）、随机型、放置型，用来跑平衡和确定性闸口。机器人用自己的随机数，不碰游戏的随机流。

## 表现层（`packages/iso`）

表现层把模拟状态画出来、把领域事件演出来。它只读状态；游戏 app 里唯一能影响模拟的方式是发命令。
接口契约（`IsoWorld`、`IsoCamera`、`Site`、`Person`、素材格式）见 [iso-architecture.md](../iso-2.5d/docs/design/iso-architecture.md)（已归档，ADR 0027），决策见 ADR 0019。

### 画法

- **2:1 等距，Q/E 转 90°**：静止时只停在 4 个角，缩放是离散档位（`ZOOM_STEPS`，`zoom` 就是每米缓冲像素 `k`）。
- **软件光栅**：画进一张低分辨率缓冲（`Uint32Array`），再放大到画布（`image-rendering: pixelated`）。
- **分层**：背景（天空、群山）→ 静态层（地面贴图 + 建筑、看台、围网、树，按转角、缩放、昼夜档缓存，设施状态变了重烘）→
  动态层（人、球、道具、粒子，每帧画，用深度缓冲被前面的建筑挡住）→ DOM 叠层（地点牌）。
- **轻量场景图**（`core/graph.ts`）：照 three Object3D 的子集写（`Node`、`Group`、`Box`、`Sprite`、`Custom`），所以活动库和人物的演出代码基本原样保留。
- **素材是字符画**（`art/`）：人物、道具、图标、像素字、小动物都是文本，字母是换色槽位，运行时按外观烘焙并缓存（`bakeArt`）。不放图片文件。
- **昼夜和天气**：`createDaylight` 按游戏分钟给天色、夜色和灯光强度；夜里的灯光池烘进地面贴图；雨丝在 `ambient/rain.ts`。
- 核心（场景图、光栅、投影、素材烘焙、地面贴图）不碰 DOM，能在 node 里测；只有 `view.ts`、`camera.ts`、`world.ts` 碰画布和指针。

### Site 接口（ADR 0016、0019）

一张地图在画面这一侧要提供的东西都在 `site/site.ts` 的 `Site` 接口里：

- 锚点中心、站位、两个地点之间的步道折线（`routeLine`）。
- 每个地点上的球场框（`courts`）和空地（`grounds`）。
- 地面高度、园区范围、起始天色。
- 相机预设和范围（`IsoCameraPose`）、活动动画库的场地风格（`venue`）。
- 建静态场景（`build`）、设施状态的画面层（`createOverlays`，带可选的磨损 `wear`）、天空和远景（`createSky`），都接 `IsoWorld`。

`apps/game` 只认这个接口（加上 `createIsoWorld` 用的地台范围），不引用地图内部的模块。

### Indian Wells 场景（`site/indian-wells/`）

- `layout.ts`：布局常量、球场框、锚点和站位、步道路网、最短路、步行分钟数。
- `ground.ts`：地面贴图（场地、步道、沙地、草坪）、浮空岛范围 `SLAB`；`build.ts`：静态节点（围墙、看台、会所、泳池、棕榈、网和围网、灯杆……）。
- `state.ts`：设施状态 → 画面档位（荒废、清理过、复原、掉档）；`overlays.ts`：设施状态一变就按新状态表重建地面和节点，每段有自己的种子随机流，结果确定。
- `wear.ts`：状况往下掉时长出的积沙、杂草和垃圾（准则 6"先出画面信号，再掉档"）；`sky.ts`：云、鸟、风滚草。
- **场地坐标系**（`world/frame.ts`）：每块场地一个旋转的局部坐标系，原点在球网中心。

### 人物和演出

- 人物是约 8×14 像素的精灵（`people/`，小孩约 7×10）：两个朝向，左向由翻转得到，按姿势、击球分段、手势、走路相位取帧；外观按 `PersonOptions` 给槽位换色，在 `apps/game/src/scene.ts` 的 `LOOKS` 里按人物 id 配。
  画面每帧调 `setPeopleView(ang, k, spriteScale)`，人物据此选朝向、换算挂点。
- **活动动画库**（`activities/`，ADR 0010）：上课、试训、比赛、清理、烧烤会、拔河等，由原子动作和时间轴（`choreo/`）编排，输入是场地框、条件和参数，可以借用游戏里现成的人物，演完还回去。API 和搬家前一样。
- 游戏里，模拟的 performance 名字通过 `apps/game/src/perform.ts` 映射到活动库；有人在岗位或工单上干活，就在那个地点的第一块球场上演。

### 相机

`IsoCamera`（`core/camera.ts`）：拖动平移、双指和滚轮按档位缩放、Q/E 旋转，`project` / `unproject` 给 DOM 叠层和拖放落点用；参数由 `Site` 的相机预设提供。
卡打开或设施修好时，相机目标点移过去几秒（玩家 5 秒没操作才接管）；`occludedBottomPx` 让目标点落在没被 HUD 挡住的那部分屏幕中间。

## 游戏 app 和界面

`apps/game` 把三边接起来：

```text
真实时间 → Session.frame() → advance() → 领域事件
                                    ├→ Projector（project.ts）：HUD 快照、快讯、地点牌、地点清单、说明面板
                                    └→ GameScene（scene.ts）：员工走位、演出、设施画面层、天气、园区日常（life.ts）
玩家拖人 / 点地点牌 / 选卡 → Session.assign / choose → 命令
```

- **Projector** 从状态算出给界面的快照（纯数据），`packages/ui` 的 Preact 组件只渲染快照、回调动作。
- **地点牌和标签**（`labels.ts`）是 DOM 叠层，按锚点每帧投影；拉远时缩成小圆点。
- **文案**全部走 i18n 键（`text.ts`），代码里不写死文字。
- **自动存档**（`persist.ts`）：IndexedDB 一个键，每天收盘和每 30 秒存一次；`?new` 或 `?seed=` 开新局。
- **调试面板**（\` 键，开发版或 `?debug`）：改状态量和标记、看导演此刻会抽哪些卡和概率并强制打开、跳过时间、导出"存档 + 命令日志"、用指定种子开新局。
- **试玩桥接口** `window.__td`：`fastForward`、`assign`、`answer`、`tap`、`pick`、`sheet`、`targets` 等，`tools/playtest/server.mjs` 通过它像回合制一样玩。

## 内容管线（`packages/content`）

所有内容用 YAML 写，构建时校验并编译成 JSON；开发模式下改 YAML，游戏不重启就换上新内容（出错时浏览器里显示错误浮层）。

| 类型 | 位置 | 内容 |
| --- | --- | --- |
| 地图 | `acts/indian_wells.yaml` | 开局时间和状态、营业时间、设施初始状态和状况、开局人物、锚点、导航图、季节、天气、开局卡和日历、导演、规则（质量目标、会员和声望漂移、会费、派生量、失败条件、总监成长） |
| 设施 | `facilities.yaml` | 每个设施的状态：场地数、质量贡献、收入、维护费、每天衰减 |
| 岗位 | `posts/<id>.yaml` | 一个持续岗位 |
| 工单 | `orders/<id>.yaml` | 一张工单 |
| 事件卡 | `events/indian_wells/<id>.yaml` | 一张卡 |
| 活动 | `activities/<id>.yaml` | 时长、地点、演出、结算效果（现在没有用到） |
| 人物、特质 | `people/*.yaml`、`traits.yaml` | 人物的能力、工资、特质；特质修正 |
| 状态量 | `stats.yaml` | 注册表：范围、显示方式 |
| 导演 | `directors/*.yaml` | 三份配置 |
| 文案 | `i18n/zh.yaml`、`i18n/en.yaml` | 所有显示文字（含 `ui.*` 界面文字） |

写法和示例见 `docs/content-guide.md`。

**校验**（`compile.ts`，构建时、热更新时、CI 都跑）：

- 报错：schema；所有引用（卡、活动、锚点、状态量、设施和设施状态、人物、文案键）；表达式和变量名；倒计时卡要有默认后果；文件名等于 id。
- 警告：只读不写的标记、效果相同的选项、只改暗处标记的选项、永远不会出现的卡、什么都不做的岗位和工单。

## 存档与版本迁移

- **存什么：** 格式标记、存档版本、内容版本、完整 `GameState`、命令日志。
- **迁移：**`save.ts` 里按版本号一级级升级（0→1→…→6）。v5 去掉了跨幕继承（`legacy`）；v6 给每个人加了球技，内容里后来加的候选人在招的时候按内容补上。读到更新版本的存档报错；内容版本不一致只警告。
- **内容 id 不改名。** 设施、岗位、工单、卡、人物、标记的 id 上线后不再改；要改就在迁移函数里映射。
- **跨幕继承已经去掉**（ADR 0016），原来的 `carryOver` / `Legacy` 设计作废。

## 扩展点

| 想加什么 | 改哪里 | 要写代码吗 |
| --- | --- | --- |
| 一张事件卡 | `events/indian_wells/<id>.yaml` + 文案 | 不用 |
| 一个岗位或工单 | `posts/` 或 `orders/` + 文案（工单可加 `locked` 预告） | 不用；要演出的话用已有的 performance 名字 |
| 一个设施状态（例如再修一级） | `facilities.yaml` + 修复工单 + 画面档位（`site/<map>/state.ts`、`build.ts`） | 画面层要写 |
| 一个候选人、一个特质 | `people/`、`traits.yaml` | 不用（长相在 `scene.ts` 的 `LOOKS` 里加一条） |
| 一个状态量 | `stats.yaml` 注册；要上 HUD 改 `project.ts` | 上 HUD 要写 |
| 一种导演风格 | `directors/` | 不用 |
| 一种新效果或条件 | `content` 的 schema 和编译器校验 + `sim/effects.ts` 或 `vars.ts`；`COMPUTED_VARS` 两边一致 | 是 |
| 一种新活动演出 | `iso/src/activities/` 写演出 + `apps/game/src/perform.ts` 映射 | 是 |
| 一张新地图 | `iso/src/site/<map>/` 实现 `Site` + 一份地图 YAML 和内容 | 只写场景 |
| 一个修复变体或升级（v0.5 提议） | `facilities.yaml` 的变体 + 带 `variant` 的修复工单或带 `worker` 门槛的升级工单 + 文案 + 画面档位 | 画面层要写 |
| 一块会开的地（v0.5 提议，ADR 0021） | 地图配置的 `parcels`（变体、锚点、导航边、工单、岗位）+ `site/<map>/` 里这块地的画面层 | 画面层要写；编译器会把每个变体走一遍 |

## v0.5 提议对架构的影响（还没做）

设计文档 v0.5 有三块提议：修复分叉和升级改造、三次选路、地图长大（ADR 0020 修订、ADR 0021）。这一节写清它们落到代码上要动哪里，派任务时对照 backlog 的 B1–B3。**现在的代码一行没改。**

### 模拟和状态

- **设施的变体和升级（B1）：**
  - `facilities[id]` 除了状态，再记下选了哪个变体、做过哪些升级。
  - 修复工单可以带变体：第一个人到场、扣材料费时锁定，沿用现有的开工规则。
  - 改造工单把设施换到另一个变体，这一周停用。
  - 升级和成长解锁靠工单的 `worker` 条件（谁在岗、能力多少），和 ADR 0020 的员工成长共用。
- **牌匾（B1）：** 修好一处就记一条（设施、变体、带队的人、第几天），放在状态里，因果日志和快讯从这里取。
- **星级和选路（P1、B2）：**
  - `stars`、`trophies` 是计算变量，`COMPUTED_VARS` 两边一致。
  - 升星发领域事件，★2、★3、★4 同时排上选路卡。
  - 选的路记在 `flags` 里，后面的条件和效果按它判断。
- **地块（B3）：**
  - 每块地记三样：状态（未开、施工、启用）、种子挑中的变体、★3 或 ★4 选的用途。
  - 导航图由"基础图 + 已启用地块的点和边"组成，只加不挪，现有锚点和边永远不变。
  - `World` 的导航缓存要按"哪些地块已启用"分开。
- **结局（P4）：**
  - 第 112 天不再判输，改为结算打分；破产照旧判输。
  - 第二季的入口先占位。

### 内容

- **`facilities.yaml`：** 每个设施列出变体：id、文案、岗位、数值、画面档位。
- **修复和改造工单：** 加一个 `variant` 字段。
- **升级工单：** 加 `worker` 门槛。
- **地图配置 `acts/indian_wells.yaml`：**
  - `stars`：每星的清单和开出的机制；
  - 选路卡和赛事日历；
  - 表演赛四期；
  - `parcels`：每块地的手画变体，每个变体带锚点、站位、导航边和分钟数、清理工单、启用后的岗位。
- **编译器校验：**
  - 每个变体的 id 唯一；
  - 每块地的每个变体都能从基础图走到；
  - 分钟数等于步道长度 ÷ 1.6；
  - 不同变体的分钟差在 ±10% 以内（初值）。

  出错是编译错误，不在运行时才发现。
- **改 schema 时的规矩：** 新的效果和条件照 CLAUDE.md 的规矩，schema、编译器、`effects.ts` / `vars.ts` 一起改。

### 画面（`packages/iso`）

- **变体的画面层：** `site/indian-wells/state.ts` 的档位按"设施 · 变体 · 状态"取。另加一个只给预览用的半透明版本。
- **地台会长大（ADR 0021）：**
  - `createIsoWorld` 的 `slab` 从一个矩形变成几块拼出的轮廓（或多边形）；
  - `IsoView` 的地台侧面按合并后的整体画，土层按高度对齐，切角只留在外角；
  - `GroundPainter` 覆盖合并轮廓的外框，轮廓外的纹素透明。

  这些改的是 iso 的接口，要同时更新 [iso-architecture.md](../iso-2.5d/docs/design/iso-architecture.md)（已归档，ADR 0027）。
- **地块的画面：** 伏笔（砌死的南门、荒掉的高尔夫西段、天上的小岛）和每块地每个状态的画面层，都加在 `build.ts`、`ground.ts` 构建顺序的最后，或者用单独的随机流。地块没启用时，原来那座岛的像素必须一个不差。
- **Site 接口：**
  - 锚点、站位、`routeLine` 要能按已启用的地块增减；
  - 相机范围跟着岛的外框变；
  - 游戏照旧只通过 `Site` 拿地图（ADR 0016）。

### 游戏 app 和界面

- **地点清单：** 加变体行（缩略图、换来、付出）。点一个变体，场景叠上预览层。
- **选路卡：**
  - 场景里画出两个选项的半透明预览；
  - 点一个选项，相机先飞过去；
  - 地块启用时，相机飞过去停一拍再回来。
- **HUD：** 加"回到会所"按钮。拿着人拖到屏幕边时，画面自动平移。
- **新的界面文字：** 照规矩放进 `ui.*`，中英两种语言都要有。

## 工程实践

- **测试：** 见 [testing.md](testing-v0.2.md)。单元测试、内容校验、确定性、机器人平衡区间、组装测试都在 `pnpm test` 里。
- **CI**（`.github/workflows/ci.yml`）：类型检查 → Biome → 分层规则 → 测试 → 构建。任何一步失败就红；main 上合并前必须绿。
- **命令：**`pnpm game`（开发版游戏）、`pnpm check`（全套检查）、`pnpm content`（编译内容）、`pnpm sim bots|playability|determinism`（报告）。
- **协作：** 分层由工具强制；重要决策写 ADR；提交信息用 Conventional Commits；代码改动走分支和 PR，文档可以直接推 main；`CLAUDE.md` 写明给 AI 协作者的规则和"不要做的事"。

## 风险

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 动画逻辑里偷偷改数值 | 存档、回放、测试全部失效 | 分层规则禁止 iso 写状态；确定性测试；待补"有无画面一致"测试 |
| 画面步道和内容导航图对不上 | 人走的路和花的时间不一致 | `game.test.ts` 检查两边相差不超过 1 分钟 |
| 改场景时破坏 `Site` 约定 | 地点牌、演出、走位错位 | 复用 `layout.ts` 的锚点、站位和球场框；组装测试兜底；重建画面回归 |
| CPU 光栅在低端安卓上慢 | 帧率低、发热 | 静态层缓存，每帧只画动态物件；看 `IsoView.stats`；必要时降缓冲分辨率 |
| 设施状态一变就重烘静态层 | 换档那一帧卡一下（约 100 ms） | 同一轮的多个 `set` 合并成一次重建；旋转、缩放途中不缓存 |
| 存档格式变动 | 测试玩家的存档失效 | 每次改格式都写迁移函数 |
| 地块启用后导航和画面对不上（v0.5） | 人走到岛外、分钟数错 | 编译器遍历每块地的每个变体；`game.test.ts` 照旧对分钟数；只加不挪 |
| 加新地打乱原来那座岛的像素（v0.5） | 截图基线全变，看不出真正的回归 | 新东西加在构建顺序最后或用单独的随机流；地块没启用时和基线逐像素一致 |
| 岛变大以后静态层更大（v0.5） | 手机上烘焙更慢、内存更多 | 先定"基础地台 + 所有地块"的最大面积；在中档手机上用最远一档量帧时间 |
| 多个协作者（含子 agent）同时改 i18n 和内容 | 合并冲突 | 按轨道分任务（backlog）；界面任务只加 `ui.*` 键 |
