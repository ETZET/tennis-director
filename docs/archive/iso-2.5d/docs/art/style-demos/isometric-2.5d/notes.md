# 2.5D 等距像素风 · 说明

## 风格
固定 2:1 等距（dimetric）镜头，全部用代码画，没有图片也没有库：自己写的软件光栅器把画面画进低分辨率缓冲（桌面每个像素 2 CSS px，手机 1 CSS px，也就是 3 个设备像素），再用 `image-rendering: pixelated` 放大。
- 地面：每个等级在世界坐标里先烘一张 0.2 m/texel 的“俯视贴图”（球场线、裂缝、沙堆、草坪割纹、建筑影子、夜里的灯光池），每帧再反投影采样。所以像素干净，旋转也不用另画。
- 立体物件：挤出的等距方块、四坡屋顶、圆柱，再加上棕榈、人、伞、旗子这些精灵，按脚底占地做拓扑深度排序。
- 昼夜：所有颜色都走一次调色板夜色，窗户、灯泡、泳池和喷泉用自发光色，光晕用 Bayer 抖动叠加。等级切换用像素溶解过渡。Q/E 平滑旋转 90°（约 0.45 秒缓动，停下时对齐等距角），投影矩阵按任意角度实时计算。
- 整块场地做成悬空的“立体模型”，带地层侧面，背景是画出来的天空和山。

## 优点
- 像 Kairosoft / 主题医院那样一眼看得懂：每块场地、看台、会所、泳池、喷泉轮廓都很清楚，人有描边，在场地上很显眼。
- 2D 的制作成本，却有体积感、遮挡和投影。旋转、夜景、动态灯光几乎不用加美术。
- 三个等级的差别很大：裂缝和沙堆、木板封窗、空泳池和绿藻、风滚草，对比满场观众、遮阳伞、串灯。Lv3 夜景（泛光灯球场、暖色窗户、彩色串灯、发光泳池）氛围很好。
- 性能：headless 软件渲染每帧大约 16–24 ms，真机会更快。只有一个文件，大约 70 KB。

## 缺点
- 小人只有 5×9 像素，表情和动作有限；镜头拉近时人不会跟着变精细（只按整数倍放大）。
- 斜的细线（网、栅栏、灯杆）在像素栅格上会出锯齿和断点，铁丝网比较“重”。
- 软件光栅占 CPU；如果场景再大好几倍，或者人物上千，就得把地面缓存起来，或者改用 WebGL。
- 大物件互相交叠时，拓扑排序偶尔会出错（目前没看到明显问题）。

## 手机可读性
竖屏默认按围墙宽度铺满（390 px 宽），能看清每个设施和每个人（大约 9 CSS px 高），标签很清楚。缺点是上下有大片天空和地面空着，等距菱形天生是横向的。双指缩放以后人物会按 2 倍、3 倍放大，读起来很舒服。建议游戏里在手机上默认放大 1.5 倍左右，再配合拖动。

## 做到可上线的成本（估算）
- 8 个设施 × 3 种状态：现在是程序生成，再精修每个设施的细节（比如手绘一些贴片：会所立面、看台座椅、招牌字），1 名像素/技术美术大约 3–5 周。
- 大约 40 种人物：换色系统已经有了（肤色、发色、衣服、帽子、裙子、球拍）。要上线需要 4 方向 × 走路 4 帧 + 挥拍 / 坐 / 欢呼 / 游泳，可以直接手绘 16×24 的精灵表，大约 2–3 周；如果全用程序换色，基础体型只要 6–8 个。
- 合计大约 1 人 1.5–2 个月。比体素 3D 的“建模 + 调光”便宜，比纯 2D 平面贵一点。

## 和现有代码的关系
- `packages/render` 现在是 three.js r187 体素渲染。2.5D 有两条路：
  1. 直接替换：用 Canvas2D（或者 PixiJS / WebGL 精灵）重写 render 层。layout.ts 的世界坐标（米）、路网、锚点可以直接用（这个 demo 就是这么用的），模拟层和 Preact HUD 都不用动。
  2. 折中：保留 three.js，换成正交相机 + 固定 45°/30° 视角 + 关掉抗锯齿的低分辨率渲染目标 + 调色板后处理，体素模型就能做出“像素等距”的感觉，资产不用重做，但不会有这个 demo 这么“手绘像素”的质感。
- 标签、HUD 继续用 Preact 盖在 canvas 上；世界坐标到屏幕坐标就是一个 `P(x,y,z)` 函数。

## 风险
- 美术风格要靠像素美术把关，程序生成很快会碰到天花板（人物和建筑细节）。
- 竖屏手机上等距视角浪费上下空间，要设计好默认缩放和镜头跟随。
- 旋转途中（例如 45°）像素线条会变形，所以只在动画里经过，静止时只停在 4 个等距角；缩放也最好用整数档位。转完最后一帧要重画背景群山（约 80 ms 的一次卡顿），上线前要把群山缓存起来。
- CPU 光栅在低端安卓上需要实测；必要时把静态层缓存起来，每帧只画动态物件。
