# 0003 M0 先原样拆分，再单独升级 three.js

- 状态：已采纳
- 日期：2026-10-30

## 背景

原型是单个 HTML 文件，从 CDN 加载 three.js r128。迁移要同时做两件会改变画面的事：拆成模块，和升级到当前稳定版（r186）。升级会改变色彩管理、光照强度单位等默认行为，画面会偏色偏暗。两件事一起做，出了问题分不清是哪一步造成的。

## 决定

- M0-2 只拆分：npm 安装并锁定 `three@0.128.0`，与原型同一版本，画面必须逐像素一致。
- M0-3 单独升级 three.js，对照四个角度的截图调光照。
- 原型保存在 `prototypes/hollow-creek.html`，作为对比基准，不修改。

## 场景构建顺序就是画面

原型用一条种子随机流（mulberry32，种子 1974）生成所有石块、杂草、裂缝和颜色抖动。拆分时，每个构建函数都必须按原来的顺序、原来的次数取数，连循环条件里每轮重新取随机数这种写法也要保留。`packages/render/src/scenes/hollow-creek/build.ts` 的步骤顺序因此是固定的：新东西加在最后，或者用单独的随机流。

## 演出里的随机数

写死的演示剧情（喂球、匹克球回合、台词）用 `Math.random`，而 three.js 生成 UUID 也调用 `Math.random`。Vite 打包时会摇掉 three 里没用到的模块级对象，取数次数随之变化，所以演出中的随机回合和原型不会逐帧相同（原型本身每次刷新也都不同）。

因此画面回归在第 0 秒暂停演出后截四个角度。演出逻辑是否一致，另外用分离 UUID 随机流的追踪验证过一次（见 M0-2 的提交说明）。M1 起演出的结果来自模拟核心的种子随机数，这个问题随之消失。

## 后果

- M0-2 的闸口是确定的：`pnpm screenshot --against prototype`。
- M0-3 改动画面时，先更新基准图并在提交里附上前后对比。

## 修订（2026-11-03）

ADR 0019 取代了这里 three.js 相关的部分：画面换成 Canvas 2D 软件光栅，three、`packages/render` 和 Hollow Creek 场景都已删除，不再升级 three.js。
"场景构建顺序就是画面"的规则保留，现在适用于 `packages/iso/src/site/<地图>/` 的 `build.ts` 和 `ground.ts`。
