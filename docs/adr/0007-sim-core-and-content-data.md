# 0007 模拟核心和内容数据（M1）

- 状态：已采纳
- 日期：2026-10-30

## 背景

技术文档 M1 要求：一个不依赖画面的模拟核心（时钟、状态、命令、事件引擎、导演），存档和迁移，sim-cli；内容全部写成 YAML，构建时校验并编译成 JSON。闸口是"同种子跑 1000 局结果一致"。

## 决定

- **时间**：一个 tick 等于 1 游戏分钟。俱乐部营业时间之外（第一幕是 20:00–8:00）直接跳过，收盘时结算这一天。倒计时、冷却、后续事件都用绝对游戏分钟；`1d` 就是第二天的同一时刻。游戏里 1× 每秒走 4 分钟，一个营业日（12 小时）大约 3 分钟（M2 试玩后从 8 分钟改的，见 ADR 0008）。
- **状态**：`GameState` 是普通对象，能直接 `JSON.stringify`；随机数是状态的一部分（mulberry32 的内部状态存在 `state.rng`）。
- **纯函数接口，内部可变**：`step()` 先复制再推进，输入不变；`advance()` 就地修改，给游戏主循环和机器人用（一局 30 毫秒，1000 局一分钟）。两者走同一套代码。
- **命令**：`chooseOption`、`moveDirector`，以及只在开发版用的 `debug*`。被接受的命令连同时间写进命令日志；种子加命令日志可以完整重放（`replay`）。
- **系统顺序**：日历和后续事件 → 活动 → 项目质量 → 事件倒计时 → 导演抽卡 → 时间加一 → 总监走位。人员、经济、会员、声望、派生状态量和失败条件在收盘时结算。
- **事件引擎**：storylet 模型。里程碑、日历、后果卡按时间表打开；阈值卡和随机卡由导演每隔一段时间筛出满足条件、不在冷却中的卡，按"卡的权重 × 导演给这个语气的权重"抽一张。倒计时到了执行默认后果。
- **效果是白名单**：改状态量、设标记、改设施、安排后续事件、开始活动、招人开人、改人的属性、写日志、结束本幕、「谁跟我走」。每次执行写一条因果日志，带着原因和引出它的上一条（`parent`），界面据此讲"因为……所以……"。
- **表达式语言**（`@td/shared/expr`）：活动结果公式、导演的压力和权重、日常漂移都写成表达式，例如 `round(2 + stat.reputation / 15 + rand() * 3)`。内容编译时解析并检查变量名，模拟运行时求值，`rand()` 用状态里的种子随机流。
- **内容**：`packages/content/data/**/*.yaml` 用 zod schema 校验，交叉检查所有引用（卡、活动、锚点、状态量、设施状态、人物、文案键、表达式变量），输出到 `src/generated/content.json`（提交进仓库，`pnpm check:content` 检查它和 YAML 一致）。只被读、从未被写的标记，以及效果完全相同的两个选项会给出警告。
- **导航图在内容里**：模拟只用它算总监走到某处要几分钟；画面另外按同样的锚点名给出每条边的路径点。
- **存档**：带版本号的状态快照加最近 500 条命令。`MIGRATIONS[n]` 把第 n 版升级到第 n+1 版，每个迁移配一份旧存档样本做测试。

## 后果

- 加一张卡、一个活动、一个导演配置只需要加 YAML 文件；新增"一类"效果或条件才需要改 `@td/sim` 和 schema。
- `pnpm sim determinism --games 1000`：每局用命令日志重放一次、原样重跑一次，状态哈希必须一致。M1 闸口在提交时通过。
- 平衡还没调：贪心机器人目前每局都赢，留给 M3 的跑局报告。
